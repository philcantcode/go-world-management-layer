# Deployment profiles and effective policy

Use this when enabling the shipped Docker/directory physical composition or
changing an image, policy, material selection, target template, run plan, or
observer adapter.

## What is authoritative

Physical plans do not come from client-supplied resource values. The operator
provides one absolute `-deployment-profile` path to a non-empty, regular JSON
file no larger than 4 MiB. The file must use schema version `2` and declares:

- one security scope;
- strict policy YAML sources by immutable `metadata.name@metadata.revision`;
- regular material source files with exact digest, size, logical path, mode,
  role, sensitivity, selection, and scope;
- authorized acquisition plans, including input selection, agent image, and
  resource plan;
- optional Linux target templates and target-run material plans;
- optional process-observer executables, arguments, environment, readiness and
  version probes, coverage, placement, resources, and byte limits; and
- the exact association between every acquisition/target plan and its policy.

The loader rejects unknown JSON fields and duplicate JSON keys. The profile and
policy sources must be regular files, not symlinks or special files; each is
read from the same inode inspected by the loader and within its size bound.
All Docker images are normalized `repository@sha256:<digest>` references and
must already be present with that exact identity. Material declarations are
checked against the bytes beneath the configured source root before startup can
continue.

Observer definition keys and collector references use the collector-name
grammar: 1 to 128 ASCII bytes; begin and end with a letter or digit; interior
characters may additionally be `.`, `_`, or `-`. Slashes, whitespace, Unicode,
and longer names are rejected before run mutation. The name participates in
the exact authority-selected `CollectorPlan` and the shared domain-separated
child-idempotency derivation, so renaming a collector changes its durable
identity rather than creating an alias.

The built-in Linux parent-death guarantee applies to the adapter process
started directly by the daemon. An adapter that daemonizes or leaves helper
processes behind is not a supported crash-reconcilable observer unless the
deployment adds and qualifies an authoritative external cgroup/process-tree
supervisor with an equivalent death proof.

The maintained executable example is generated by
[`testdata/e2e/run-world-e2e.ps1`](../../testdata/e2e/run-world-e2e.ps1). Its
strict policy template is
[`policy/deployment/e2e-directory-copy.yaml`](../../policy/deployment/e2e-directory-copy.yaml).
Use the script as a field-shape example, not as a production policy or static
image pin.

## Compile and preflight

Probe the same Docker settings that the daemon will use:

```powershell
go run ./cmd/world-capabilities `
  -docker-binary docker `
  -linux-target-driver docker `
  -workspace-driver directory `
  -policy .\policy\deployment\e2e-directory-copy.yaml
```

Match `-target-allow-ptrace` and `-agent-container-user` to the intended daemon
when they differ from their defaults. `world-capabilities` does not provision a
container. It currently probes only `observer-driver=none`; an exact
profile-defined process-observer fingerprint is compiled by daemon startup, so
the standalone tool cannot precompute that composition. It reports component
and combined fingerprints, the physical-policy facts, and, when `-policy` is
supplied:

```json
{
  "effective_policy": {
    "reference": "name@revision",
    "digest": "sha256:...",
    "capability_fingerprint_digest": "sha256:..."
  }
}
```

At daemon startup the profile is loaded first, then every selected driver and
observer configuration is probed. The daemon builds one complete capability
fingerprint, compiles each policy source against it, verifies that the declared
reference matches the policy metadata, binds the resulting digest pair into
every acquisition and target plan, and sends every published plan through the
same physical-policy checks used immediately before mutation. Only after all
plans pass does it publish the effective policies to durable control state.
The listener is not opened during any of these steps.

Admission then re-resolves the durable effective-policy pair and the exact
physical plan immediately before each relevant mutation. Checks include lease
TTL, runtime/image/user/isolation, network, workspace mode, target template and
reset/recovery mode, capture/export limits, target concurrency, exact live
physical-policy reports, and aggregate CPU, memory, and capture resources. The
aggregate calculation inventories every durable session and re-resolves its
persisted plans; caller-provided totals are not trusted. A retry excludes its
own already-bound candidate once instead of consuming capacity twice.

## Required daemon selection

The physical Linux combination is:

```text
agent-driver=docker
workspace-driver=directory
linux-target-driver=docker       # required when the profile has targets/runs
observer-driver=process          # exactly when the profile has observer adapters
capture-driver=ledger            # optional policy-authorized local capture
material-driver=local
```

`agent-driver=docker` and `workspace-driver=directory` must be enabled
together. A Docker Linux target requires that pair. Android and physical-device
driver selections currently accept only `none`.

Every state/source/workspace/target/observer/capture/ledger/bundle/material
root, the deployment profile, and a configured Unix socket must be absolute
and pairwise non-overlapping in physical mode. Do not put the database or
profile beneath a workspace, target, material source, or publication root.

## Change procedure

1. Drain admission and finish or explicitly fail active work.
2. Build and inspect new images; record their repository digests, not mutable
   tags.
3. Create a new policy revision for any semantic or enforcement change.
4. Update the immutable material declarations and recompute every affected
   digest and size.
5. Run `world-capabilities -policy` with the exact intended driver settings.
6. Generate a new version-2 deployment profile and preserve its digest with the
   rollout evidence.
7. Start a quarantined canary. Treat a compile, image inspection, plan
   preflight, root-separation, or startup reconciliation failure as a hard stop.
8. Run the Docker end-to-end qualification and inspect `evidence.json` before
   opening production admission.

Never retain an old digest through a compatibility alias. A changed policy,
capability fingerprint, image, runtime, observer, material plan, or physical
enforcement fact is a different realization and must bind a new generation.
